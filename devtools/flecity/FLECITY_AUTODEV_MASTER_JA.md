## 0. 今回の最重要目的
私はFlecity向けFiveMアプリ・リソースの開発者です。就寝中・仕事中にローカルAIが、安全な範囲で開発・バグ修正・検証・UI改善を続け、帰宅後に「何が変わったか・何がPASSしたか・どの画面が変わったか・何を承認すべきか」を日本語で確認できる状態を作ってください。

**単なる実装案ではなく、今のPCで実装・検証・設定できる範囲を実行してください。** ただし安全境界、ユーザー承認、利用可能な製品機能、利用枠、サーバー環境を偽らないでください。対応していない機能は未実装/未対応として報告してください。

### 環境（実物を調べて確定する）
- ソースルート: `D:\FiveM_Dev\application`
- FiveMテストサーバー: `D:\FiveM_Test_Server`（既存稼働サーバーを利用。別サーバーや別ライセンスキーは不要）
- 構成の目安: QBox 2.5.4 / oxmysql / LB Phone 2.9.0 / MariaDB / citizenid=CSN
- ソース管理: **ローカルGit優先**。GitHub Actions/Push/PRを前提としない。ネットワークから勝手にfetch/pullしない。
- 既存の `devtools/flecity`、Resource Registry、検証用 `flecity_validation_bridge`、Lua 5.4、テスト群、バックアップ、過去レポートを必ず最初に調査し、**作り直さず再利用**。
- 旧名称・別名: LINK=旧PARTY（`flecity_games` 内の可能性）、LOOP=旧PLAY（同一リソースの可能性）、フレプリ=`puribooth`、プリフォト=`puriphoto`、BASE=`flecity_base`、WAVE（配置未確認）。実際の配置は台帳照合で確定。

## 1. 着手順序（第一回のタスク）
1. `git status`、現在のブランチ、未コミット差分、直近コミット、既存テスト・ブリッジ・ツール・レポートを**読み取り専用**で棚卸し。中断した作業を上書きしない。
2. `devtools/flecity/NEXT_SESSION_JA.md` など既存の引き継ぎ文書を探して読み、これまでの結果と未実施を区別する。ファイルがなければ作成。
3. 共通基盤が実際に動くことを非破壊テストで確認し、既存の実装と重複しない最小差分のみ追加する。
4. 自動開発の対象・承認境界・リソース台帳・日報・中断復旧・定期実行を実装。
5. **ドライランを1回成功させてから**、承認不要な範囲だけの定期実行を有効化。定期実行機能の可否、正確な登録日時・次回実行予定、実行条件、実行したテストを報告。
6. 最初の開発対象はBASEとLINK。その後LOOP、WAVE、フレプリ、プリフォト、将来の新規リソースへ共通機能を順次展開。

## 2. 省利用枠・マルチモデル運用
- **GPT-6 Luna（利用できる場合）を日常作業の第一候補**：小規模コード修正、ログ要約、回帰テスト追加、単純なUI問題の特定、レポート、規約に沿った修正。
- **GPT-6.1 Terra（利用できる場合）**：スクリーンショット読解、UI・操作画面のレビュー、視覚的なズレの検討。
- **GPT-6.1 Sol / 利用可能な高性能モデル**：複雑なバグ、DBトランザクション、権限・セキュリティ、並行処理、設計変更、難解な不具合のレビュー。
- モデル名・利用可否・Codexアプリ/CLIのモデル切替と自動分配の可否は**実環境で確認**。モデルが使えなければ使用可能な最も軽い適切なモデルへ代替する。モデルを切り替えたと偽らない。
- モデルの費用とCodex/ChatGPTの利用枠は同一ではない。**軽量モデルでも共有利用枠が回復するわけではない**。毎回のタスクを小さく分割、最初に変更範囲を絞る、差分に応じた検証を行う。不要なループ・過剰なコンテキスト再読込・並列エージェント乱立は禁止。
- Claude CodeやAPI連携は調査・設計まで可能。ただし新しい有料契約、API従量課金、秘密鍵発行、インストール、ログイン連携は**明示承認が必要**。APIキーが無ければ呼び出さない。Claudeは必須ではなく、将来の任意オプション。
- Fastモード等の高消費設定を自動でONにしない。モデル切替不可ならタスク分類と推奨モデルをレポートするだけでよい。

## 3. 夜間・仕事中の自動開発
- 初期候補: **毎日02:00と13:00（Asia/Tokyo）**。ローカルCodexのスケジュール機能が使えるか実際に確認し、使用可能なら設定する。設定APIやタスクがなければ、Codex CLI + Windowsタスクスケジューラ等の**実際に動く代替**を検討してテストする。CLIのコマンドや引数を憶測で生成しない。
- 両方式を重複登録しない。**作業ロック**、実行ID、タイムアウト、起動中の二重実行回避、クラッシュ時の安全なロック回収、最大連続失敗回数、バックオフを実装。
- PCのスリープ、ログオン状態、アプリ起動、アクセス許可を確認。スリープ中の実行保証、利用枠回復の即時検知、自動で制限を突破できると主張しない。
- 利用枠不足・認証失敗時は**無限再試行しない**。既存作業保存→短い日報→次の予定時刻で再開。保存済みリセットの自動使用、クレジット購入、課金の有効化はしない。
- 自動タスクは**事前承認済みの非破壊作業のみ**を行う。画面の承認待ちで停止した場合はレビュー待ちにし、勝手に許可を迂回しない。
- レポート・スクリーンショット・ログ・バックアップの容量上限と保存期間を設定。バックアップは少なくとも別の物理ドライブ/外付け先が利用可能か確認し、なければ同一ドライブに置いたものを「耐障害バックアップ」と呼ばない。

## 4. 汎用Resource Registryと新規開発テンプレート
- 全アプリで「正式名/旧名/別名/リソース名/同一リソース共有アプリ/ソースパス/実配置先/依存関係/起動順序/テストコマンド/危険操作/バックアップ方法」を一元管理。
- 既存の台帳があれば拡張。現物を確認できないパス・ブランチは確定しない。**LINKとLOOPの共有リソース**に対する更新は両アプリの回帰テストを必須とする。
- 新規リソースの雛形作成時に台帳・最小テスト・CI相当のローカル検査・ログ/設定/権限/復旧を登録。マニュアルと日本語の導入手順をテンプレート化。
- アプリ固有のテストアダプターを持ち、共通基盤がゲーム固有実装に密結合しない設計にする。

## 5. 自動テストのレイヤーと真偽の区別
**検証階層を混同しない**：
- T0 静的/構文/依存検査（Lua 5.4、JS、HTML/CSS、fxmanifest、参照ファイル、NUI callback）。
- T1 単体/回帰/プロパティテスト（固定乱数シード、境界値、異常入力、ゲーム終局、権限チェック）。
- T2 NUIブラウザー/模擬通信（Playwright等、LB Phone相当ビューポート、カメラ/ノッチ/安全領域、クリック/入力/スクロール/画面遷移）。
- T3 **使い捨て専用DB**統合検証（トランザクション・コミット/ロールバック・並行更新・孤立データ/マイグレーション）。DB名と接続先を検査してから実行。
- T4 既存FiveMテストサーバーの稼働ログ・Resource状態・非破壊の `base_selftest` / `game_selftest` / 検証ブリッジ。自己診断の書き込み有無はソース監査してから実行。
- T5 **本物のFiveMクライアント上でのLB Phone操作**（本物のログイン/ゲーム描画・スクリーンショットが取得できて初めてPASS）。T2/T4をT5と呼ばない。
- T6 **複数の独立したFiveMクライアントでの対戦/同期**。模擬プレイヤーはT1/T3として報告し、T6の代替だと偽らない。
- 各項目はPASS/FAIL/NOT RUN/BLOCKED/FLAKYを記録。証跡（ログ・乱数シード・テストデータ識別子・差分・スクリーンショット）を保存。

## 6. LINK/LOOPのゲーム自動検証
- LINK: 将棋（合法手/成り/王手/詰み/AI難易度/千日手等の実装仕様）、リバーシ（反転/パス/終局）、ヒット＆ブロー（重複設定/評価）、コネクトフォー（縦横斜め/引き分け）、テトリス対戦（落下/消去/妨害/同期）。**実装済みの仕様をまず確認**し、未実装機能をPASSとしない。
- 2〜4人の仮想プレイヤーを使う招待・ルーム作成・手番・同時送信・再送/重複送信・無効入力・途中退出/再参加・タイムアウト・接続断・再接続・勝敗・権限の検証。
- ワードウルフ/お絵描き当ては役割配布・秘密情報の漏えい・投票/採点・描画データ同期・タイムアウトなど**機械的に検証できる部分**だけを追加。作品の面白さ・自然な会話は自動PASSにしない。
- LOOP: タワーの設置タイミングと描画・判定ズレ（ラグ疑い）、フレームレート差、低FPS/高遅延/連続入力、FALL/テトリス等の停止/リスタート/得点を重点検証。
- 課金枠・週更新・Renewed-Bankingはゲーム内の本当の残高・会社金庫に触れないモックで検証。課金操作の実サーバー実行は禁止。

## 7. UI・UX自動検査と視覚レビュー
- Playwrightなどで小さいスマホ画面、LB Phoneのカメラ/ノッチ・安全領域、異なる解像度/倍率を検証。
- 文字切れ、重なり、非表示ボタン、押せない領域、フォーカス、余白、コントラスト、スクロール、タップ可能領域、画面遷移、フリーズ、JSコンソールエラーを機械的に検査。
- ゲーム盤面の上下揺れ、将棋の成り選択、履歴スクロール、リバーシ/コネクトフォーのタップ位置、ゲームの招待/退出画面、日本語文字の見やすさを重点項目に。
- **正常な基準画像を承認済みベースラインとして保管**。意図的変更と意図しない回帰を区別し、画像差分はノイズ閾値・動的領域マスクを設定。勝手に基準画像を更新して不具合を隠さない。
- 必要に応じて画像対応AIで変更前後をレビュー。視覚レビューは主観的助言であり、ユーザー好みのデザイン変更は承認待ち。スクリーンショットが無ければ「視覚チェック未実施」と報告。
- ブラウザーNUIと本物のFiveM画面の結果を別々に記録し、実機検証がない場合はその旨を明記。

## 8. BASE・WAVE・フレプリ・プリフォト
- BASE: ワークスペース作成/招待/OWNER・MANAGER・MEMBER権限/メモ・在庫・タスク・会計/追加項目の保存・非表示保持/同時更新/不正入力時に既存値が消えないこと。実銀行・ox_inventoryは操作しない。
- WAVE: 楽曲・名義・権限/保存/再生/楽曲販売/内部DB残高と引き出しロジックの分離/サブスク収益分配/匿名制作者情報の漏えい防止。実際の銀行振込や有料購入はモック・専用データのみ。
- フレプリ: 位置設置/向き/カウントダウン/4枚撮影/構図調整/装飾/プリフォト連携/価格と台別売上集計。現実の設置済み台・売上は触らない。FiveM撮影は自動化できる段階まで段階的に。
- プリフォト: 撮影・ギャラリー読み込み・ペン/文字/スタンプ/アルバム保存/メモ/マイスポット/保存先URL失敗時。ユーザーの既存写真は削除しない。
- 新規アプリ: 共通テストテンプレートから開始し、台帳登録・ログ・復旧・UI基準画像とテスト分類をセットで作る。

## 9. 非破壊・権限・誤操作防止
**無人で許可される操作**：リポジトリ内での専用作業ブランチ作成、非破壊コード編集、静的/単体/ブラウザー模擬テスト、使い捨てDBテスト、ローカルGitコミット、ログ読取・報告作成。元データや既存リソースを変更しない範囲の既存ブリッジによる読み取り専用監視。

**個別承認が必要な操作**：既存FiveMリソースへの初回または対象を超える更新・再起動、実DBへの書き込み/スキーマ変更、権限変更、サーバー全体の再起動/停止、アカウント・課金・銀行・インベントリ操作、外部公開/提出・アップロード、外部AI契約/API課金、PC全体の権限付与、既存ファイルの大量削除。以前のブリッジ導入許可を他リソースの無制限更新許可へ拡大解釈しない。

- プレイヤー接続中のリソース更新は保留。接続人数0人でも**破壊的変更を自動承認した扱いにしない**。
- 破壊的テストは専用の使い捨てDBのみ。実DBの資格情報・Cfxライセンスキー・個人情報・APIキーをログ/チャット/Git/スクリーンショットに載せない。`.gitignore`、秘匿ファイルの権限、ログマスキングを確認。
- `git reset --hard`、`git clean -fdx`、force push、バックアップ無き大量ファイル置換は禁止。既存の未コミット変更・別タスクの編集中ファイルを尊重。
- テスト対象以外のリソース更新禁止。LINKとLOOPが同じ`flecity_games`の場合、更新の影響範囲に両方を含める。
- 自動修正は変更を小さく保ち、テスト失敗ならロールバック**候補**を確認。異常時にDBデータを手当たり次第削除しない。

## 10. 検証ゲート・性能・品質
- 各作業: 仕様/バグ再現 → 差分計画 → コード実装 → 適切な階層のテスト → レビュー → コミット → レポート。変更が小さければ無駄なテストを回さず、共有ライブラリ/共通リソースの変更では対象横断の回帰テストを実行。
- 権限はクライアント/NUIで隠すだけでなく、サーバー側で毎回認可する。SQLはパラメーター化、トランザクション/競合制御、タイムアウト、重複実行防止を優先。
- NUIの性能: JS例外、無限ループ、過剰な描画更新、メモリ増加、FPS落ち、レスポンス遅延を基準値との差で追跡。偽の性能改善率を報告しない。
- FiveMサーバーの負荷: リソースごとのログエラー、サーバースレッドの長時間ブロック、頻繁なSQL問い合わせ、負荷時のメモリ増を監視。自動診断ブリッジが新しい脆弱性にならないよう権限・起動条件・外部公開を最小化。
- セキュリティテスト: 偽citizenid、他人workspace ID、権限昇格試行、NUIイベントの不正値、不正な金額・数量・URL・UTF-8、同時リクエスト・切断時の整合。
- データ互換性: スキーマ変更は移行/戻し計画を用意、既存の保存データを維持。SQLスキーマ更新は無人で既存DBへ適用しない。

## 11. 安全な自動開発サイクルと優先順位
- 優先: (1) データ消失/権限/課金事故防止、(2) クラッシュ/ロック/通信同期不良、(3) UI操作不能/表示崩れ、(4) テストカバレッジ/メンテナンス性、(5) 小規模UX改善、(6) 新機能（仕様が既に決まっている範囲）。
- 勝手に機能削除、収益価格改定、課金条件変更、ブランド/アイコン差し替え、全面UI改装、運営提出版の更新をしない。
- 自動タスクが未設定・利用枠不足・承認待ち・依存関係欠如なら、できる非破壊タスクへ切り替えるか中止し、BLOCKEDと対処法を記録。
- 1回の自動実行に制限時間、作業数の上限、変更ファイル数の目安を設け、長時間無限開発しない。重大な問題発見時は他の作業より優先し、自動で実データに触れない。
- 多人数テスター実機検証は当面は手動最終ゲート。NPCやモックを本物の複数クライアントとして報告しない。

## 12. 作業保存・帰宅後の日報
既存の配置があれば尊重し、少なくとも以下を用意:
- `devtools/flecity/NEXT_SESSION_JA.md`: 次回起動が読む継続状態・作業優先順位・保留承認・テスト環境。
- `devtools/flecity/DAILY_REPORT_JA.md`: 人間用の最新要約（直近実行日時・全体状態・PASS/FAIL/未実施・次回予定）。
- `devtools/flecity/reports/YYYY-MM-DD_HHMM_JST/`: 各回の詳細、変更ファイル、git commit SHA、ログ、テストの階層、ブラウザーとFiveM実機の区別、必要なら画像の変更前後比較。
- `devtools/flecity/RESOURCE_REGISTRY.*`: 実態確認済みの管理台帳。
- `devtools/flecity/AUTOMATION_OPERATIONS_JA.md`: 有効な自動実行、停止/再開/緊急停止手順、実行権限、PCスリープ条件、障害時復旧手順。

日報の冒頭は次の形式にする:
1. **今日やったこと**（アプリ名ごとに3〜8行）
2. **検証結果**（階層別 PASS/FAIL/NOT RUN・根拠パス）
3. **画面比較**（画像リンク。無ければ無し）
4. **未解決・承認待ち**（承認すべき変更だけ目立つ形に）
5. **現在のサーバー状態**（リソース再起動/DB更新の有無）
6. **次回実行予定・継続タスク**
報告は日本語で、機械ログの大量貼り付けは避ける。結果が不明なら不明と明記。

## 13. 完了条件と報告
以下を**実際に行った結果**として報告すること:
- 共通基盤が既存の実装を再利用していること。
- ローカルモデル候補と切替可否（Luna/Terra/Sol/Claude連携は実際の対応状況による）。
- スケジュール機能の有無、実際の登録状態、次回の日本時間の実行時刻、利用枠不足時の動作。
- 最低1回の安全なドライランとPASS/FAIL/NOT RUN。
- BASE・LINKの既存テストを壊していないこと。
- 変更ファイル・ローカルGitコミット・バックアップ/復元検証結果。
- 未対応機能（特にFiveMクライアント本物の無人操作、複数クライアント実機、AI自動モデル切替、課金なしの外部AI利用）。
- **私が今すぐ行う必要のある操作のみ**。無ければ「操作不要」と報告。

**今回は設定構築を最優先にし、安全なドライランで検証してから自動運用を開始してください。今後の新規開発にもこの運用ルールを適用してください。**
